# 02. Core Domain Model

---

# Purpose

The Core Domain Model defines the canonical business objects of the Risk Digital Twin (RDT) platform.

These objects represent the long-term information model of the system and remain independent of implementation technologies, databases, APIs or user interface components.

Every backend service, frontend component, connector and AI capability should operate on these canonical objects.

The purpose of the domain model is to provide:

- common terminology
- stable interfaces
- reusable data structures
- traceability
- extensibility

---

# Domain Object Categories

The platform contains four categories of objects.

## 1 Configuration Objects

Created by users.

Examples:

- Monitoring Objective
- Monitoring Profile
- Information Source
- Connector Proposal
- Connector Specification
- Connector Definition

These objects change relatively infrequently.

---

## 2 Runtime Objects

Created automatically.

Examples:

Connector Execution

Raw Record

Knowledge

Risk Signal

Recommendation

These objects are continuously generated.

---

## 3 Operational Objects

Support monitoring and administration.

Examples:

- Connector Test Result
- Execution Log
- Audit Event
- Error Report

---

## 4 Reference Objects

Shared across the platform.

Examples:

- Enterprise Risk Categories
- Risk Taxonomy
- Countries
- Languages
- Connector Types
- Authentication Types

# Configuration Objects

---

# Monitoring Objective

Purpose

Defines a business objective that the platform should continuously monitor.

Examples

- Monitor geopolitical risks affecting shipbuilding
- Monitor supplier stability
- Monitor energy prices

Relationships

```
Monitoring Objective

1 ---- * Monitoring Profiles

1 ---- * Information Sources

1 ---- * Risk Signals
```

---

# Monitoring Profile

Purpose

Defines reusable filtering criteria.

Contains

- keywords
- organisations
- locations
- languages
- exclusions
- sensitivity

A Monitoring Profile represents business intent rather than connector configuration.

---

# Information Source

Purpose

Represents an external or internal information provider.

Examples

- Bloomberg
- YLE
- Reuters
- ERP
- SAP
- Weather Service

Information Sources do not describe technical implementation.

---

# Connector Proposal

Purpose

AI-generated recommendation describing how the source should be connected.

Created by

AI Recommendation Service.

Contains

- recommended connection method
- assumptions
- business scope
- AI confidence
- validation plan

Lifecycle

```
Draft

↓

Reviewed

↓

Accepted

↓

Archived
```

---

# Connector Specification

Purpose

Approved business and technical configuration.

Contains

- endpoint
- schedule
- authentication type
- mapping
- monitoring scope

Created after user approval.

---

# Connector Definition

Purpose

Executable runtime configuration.

Contains

- adapter
- parser
- polling schedule
- field mapping
- retry policy

Used directly by Connector Runtime.

---

# Runtime Objects

---

# Connector Execution

Purpose

Represents one execution of a connector.

Contains

- start time
- end time
- records processed
- errors
- duration

---

# Raw Record

Purpose

Canonical representation of collected information.

Every connector produces Raw Records.

A Raw Record contains no business interpretation.

Typical fields

- source
- title
- summary
- language
- publication time
- raw payload reference

---

# Knowledge

Purpose

Represents the canonical, reusable understanding of collected information.

Knowledge is the primary output of the processing pipeline and is independent of Monitoring Objectives.

Knowledge is produced by the Knowledge Processing Service, which may use one or more techniques including Artificial Intelligence, deterministic rules, external NLP services, or future knowledge extraction methods.

The platform stores Knowledge rather than AI-specific outputs.

Typical contents include:

entities
organisations
people
locations
events
relationships
topics
classifications
temporal information
extracted metadata
summaries
confidence values
references to supporting evidence

Knowledge is intended to be reusable across multiple Monitoring Objectives without repeating extraction.
---

# AI Enrichment

Purpose

Represents semantic understanding of the collected information.

Contains

- summary
- classification
- sentiment
- event type
- importance
- explanation

AI Enrichment builds upon Knowledge.

---

# Risk Signal

Purpose

Represents business interpretation.

Contains

- Monitoring Objective
- Enterprise Risk Category
- severity
- probability
- impact
- confidence
- reasoning

Risk Signals are consumed by dashboards.

---

# Recommendation

Purpose

Represents an AI-generated recommendation.

Examples

- Monitor supplier

- Escalate issue

- Contact logistics department

- Increase monitoring frequency

Recommendations should always reference one or more Risk Signals.

# Architectural Decision

The Core Domain Model intentionally separates:

- configuration
- runtime processing
- business interpretation
- operational monitoring

This separation enables independent evolution of each architectural layer while maintaining a stable and reusable platform.
