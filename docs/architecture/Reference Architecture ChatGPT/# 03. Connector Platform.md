# 03. Connector Platform

---

# Purpose

The Connector Platform provides a generic mechanism for integrating external and internal information sources into the Risk Digital Twin.

Its primary responsibility is to collect information, transform it into the canonical Raw Record format, and deliver it to the Knowledge Processing pipeline.

The Connector Platform deliberately does **not** perform business interpretation or risk analysis.

---

# Objectives

The Connector Platform has the following objectives:

- connect heterogeneous information sources
- minimise custom development
- maximise connector reuse
- automate connector creation using AI
- provide consistent runtime behaviour
- isolate source-specific implementation details
- support future connector types without architectural changes

---

# Connector Philosophy

A connector should be as simple as possible.

A connector should:

✓ Connect

✓ Authenticate

✓ Collect

✓ Parse

✓ Map

✓ Create Raw Records

Nothing more.

A connector should **never** contain:

- business logic
- enterprise risk knowledge
- recommendations
- Monitoring Objective logic
- AI prompts
- dashboard logic

# Information Source

The process begins when a user creates an Information Source.

Examples include:

- Bloomberg
- YLE
- Reuters
- SAP
- ERP
- Weather API
- IoT Platform

An Information Source represents a business concept rather than a technical implementation.

---

# Connector Proposal

Purpose

An AI-generated recommendation describing how the source should be connected.

Created by

Connector Recommendation Service.

Contains

- recommended connection method
- recommended adapter
- business scope
- monitoring configuration
- technical configuration
- assumptions
- automated validation plan
- confidence

The Proposal is intended for review rather than execution.

---

# Connector Specification

Purpose

Represents the approved connector design.

The Specification contains:

Business configuration

- Monitoring Objectives
- Monitoring Profile
- Languages
- Geographic scope
- Risk mappings

Technical configuration

- endpoint
- authentication type
- polling schedule
- parser
- mapping

The Specification becomes the contract between business and runtime.

---

# Connector Definition

Purpose

Represents the executable runtime configuration.

Contains

- adapter type
- schedule
- parser
- field mapping
- retry policy
- timeout
- secrets reference

The Definition is generated automatically from the approved Specification.

---

# Connector Test

Before activation every connector should be validated automatically.

Validation includes:

- connectivity
- authentication
- endpoint availability
- parser validation
- field discovery
- sample records
- deduplication
- schema validation

The result is stored as a Connector Test Result.

---

# Connector Activation

Only successfully tested connectors should be activated.

Activation creates:

- runtime schedule
- monitoring state
- execution history

---

# Runtime Execution

During runtime the Connector Runtime periodically executes every active connector.

Runtime responsibilities:

- execute schedule
- call adapter
- download data
- parse response
- create Raw Records
- log execution
- report failures

---

# Connector Monitoring

Every connector exposes operational metrics.

Examples:

- status
- last execution
- next execution
- duration
- records collected
- duplicates skipped
- failures
- average execution time

These metrics support operational monitoring rather than business dashboards.

---

# Connector Adapter Framework

Connectors are implemented using reusable adapters.

Initial adapters:

- RSS Pull
- REST Pull
- File Import

Future adapters:

- Database
- Email
- Azure Event Hub
- Azure IoT Hub
- MQTT
- Webhooks
- GraphQL
- OPC-UA

Every adapter implements the same interface.

```typescript
interface ConnectorAdapter {

    validateConfiguration()

    testConnection()

    fetch()

    parse()

    mapToRawRecords()

}
```

---

# Canonical Raw Record

Every connector produces the same output.

```text
Connector

↓

Raw Record
```

Regardless of connector technology.

The Raw Record becomes the input for Knowledge Processing.

This principle allows every downstream service to remain connector-independent.

# Separation of Responsibilities

| Layer | Responsibility |
|---------|----------------|
| Information Source | Business representation |
| Connector Proposal | AI recommendation |
| Connector Specification | Approved design |
| Connector Definition | Executable configuration |
| Connector Runtime | Scheduling and execution |
| Connector Adapter | Source-specific communication |
| Raw Record | Canonical collected data |

---

# Architectural Decisions

The Connector Platform deliberately separates:

Information Source

↓

Proposal

↓

Specification

↓

Definition

↓

Runtime

↓

Raw Record

instead of storing everything in one Connector object.

Advantages:

- versioning
- auditing
- AI regeneration
- repeatable testing
- runtime stability
- business/technical separation

---

# Future Evolution

The architecture is designed so that Connector Runtime can eventually be replaced by:

- Azure Functions
- Azure Container Apps Jobs
- Kubernetes Jobs
- Event-driven execution

without modifying the business model.

Similarly, adapters can evolve independently as new technologies become available.

---

# Guiding Principle

**Connectors collect information.**

**Knowledge Processing understands information.**

**Risk Assessment evaluates business impact.**

**Recommendations support decisions.**

Each architectural layer should remain independent.

1. Business Platform
   Monitoring Objectives
   Information Sources
   Monitoring Profiles

2. Acquisition Platform
   Connector Platform

3. Knowledge Platform
   Knowledge Processing
   Knowledge Repository

4. Intelligence Platform
   Risk Assessment
   Recommendations

5. Presentation Platform
   Dashboards
   Analytics
