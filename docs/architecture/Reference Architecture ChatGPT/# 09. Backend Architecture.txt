# 09. Backend Architecture

---

# Purpose

The Backend Architecture defines the internal structure of the AI Knowledge & Risk Intelligence Platform.

It describes how the platform is decomposed into independent services, how responsibilities are distributed, and how services collaborate to implement the business capabilities defined in previous chapters.

The backend follows a modular service-oriented architecture where each service owns a clearly defined business capability.

---

# Backend Design Goals

The backend architecture has been designed to achieve the following objectives:

- modularity
- clear separation of responsibilities
- independent testing
- scalability
- maintainability
- extensibility
- cloud-native deployment
- AI integration
- technology independence

---

# Overall Backend Architecture

```
                    REST API
                        │
                        ▼
                  Controllers
                        │
                        ▼
                   Services
                        │
                        ▼
                 Repositories
                        │
                        ▼
                  Data Storage
```

Business logic resides exclusively inside Services.

Controllers should never contain business logic.

Repositories should never contain business logic.

---

# Repository Layer

Repositories encapsulate persistence.

Examples:

InformationSourceRepository

ConnectorRepository

KnowledgeRepository

RiskSignalRepository

RecommendationRepository

Repositories perform:

- CRUD
- queries
- indexing

Repositories do not contain business rules.

---

# Controllers

Controllers expose REST endpoints.

Controllers should:

- validate requests
- invoke services
- return responses

Controllers should never:

- access databases directly
- perform business reasoning
- call AI models directly

---

# Worker Services

Some processes execute asynchronously.

Examples:

Knowledge Processing Worker

Connector Runtime Worker

Risk Assessment Worker

Recommendation Worker

Workers communicate using domain objects.

# Dependency Rules

Controllers depend on Services.

Services depend on Repositories.

Repositories depend on Storage.

Reverse dependencies are not permitted.

Knowledge Platform never depends on Presentation.

Presentation never depends on Acquisition.

Business logic always flows downward.

---

# Error Handling

Errors are classified into:

Business Errors

Validation Errors

Connector Errors

Infrastructure Errors

AI Errors

Every error should include:

- timestamp
- correlation id
- service
- severity
- details

---

# Scalability

Services should be independently scalable.

Examples:

Connector Runtime

Knowledge Processing

Risk Assessment

Recommendation Generation

These services may eventually execute on different compute resources.

---

# Future Evolution

The backend architecture supports future capabilities including:

- distributed workers
- event-driven processing
- AI agents
- semantic search
- knowledge graph
- streaming data
- autonomous recommendations

These extensions should not require redesign of the existing service boundaries.

---

# Architectural Decisions

Business capabilities are implemented as services.

Business logic is isolated from infrastructure.

Persistence is isolated from services.

Controllers remain lightweight.

Services communicate through canonical domain objects.

---

# Guiding Principle

> **Every backend service owns one business capability, communicates through canonical domain objects, and remains independent from presentation and storage technologies.**
One observation after writing these chapters.

Originally we had five platforms.

Now I think the architecture naturally separates into three levels:

──────────────────────────────────────────────
Business Architecture
──────────────────────────────────────────────

Business Platform

Presentation Platform

──────────────────────────────────────────────
Intelligence Architecture
──────────────────────────────────────────────

Knowledge Platform

Intelligence Platform

──────────────────────────────────────────────
Infrastructure Architecture
──────────────────────────────────────────────

Acquisition Platform

Backend Platform

Deployment Platform

This is actually a classic enterprise architecture decomposition:

Business Architecture — what the users see.
Intelligence Architecture — what makes your product unique.
Infrastructure Architecture — how it is implemented.
